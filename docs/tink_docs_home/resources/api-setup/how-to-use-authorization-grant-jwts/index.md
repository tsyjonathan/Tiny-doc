Tink offers a [standardized](https://tools.ietf.org/html/rfc7523) way to use JWTs in the OAuth 2.0 flow for acquiring access tokens. This allows clients to use a private key as a proof of possession, avoiding [an extra request](/Tiny-doc/tink_docs_home/resources/getting-started/get-access-token/) to Tink's authorization grant endpoint and improves security by avoiding sending a secret over the network.

For Tink to identify the signature on your authorization grant JWTs, Tink must associate your private key used for signing with a corresponding public key. This process currently involves some manual steps.

### Generate a Certificate Signing Request (CSR)[](#generate-a-certificate-signing-request-csr-)

To sign a JWT that Tink can verify, you must generate a private key and corresponding CSR.

Tink’s CSRs requirements:

-   public key algorithm is the elliptic curve _NIST P-256_ (also called _secp256r1_ and _prime256v1_)
-   hash algorithm is _SHA2-256_
-   CSR is _PEM_\-encoded
-   Common Name (CN) attribute is set to your OAuth client's ID (called `{YOUR_CLIENT_ID}` in the examples below) to avoid potential confusion with any other OAuth clients you may have or later create.

You may use the tool of your choice for generating the private key and corresponding CSR. Here is an example using OpenSSL:

Generate the private key and corresponding CSR

```
openssl ecparam -name prime256v1 -genkey -noout -out my-oauth-client.key.pem
openssl req -new -sha256 -key my-oauth-client.key.pem -out my-oauth-client.csr -subj "/CN={YOUR_CLIENT_ID}"
```

Remember to keep your generated private key secure. This will be used in later authorization API requests.

### Reach out to us[](#reach-out-to-us)

Contact your Account Manager or get in touch with [Tink Support](/Tiny-doc/tink_docs_home/resources/support/how-to-find-technical-support/) to send them the CSR file you generated, requesting authorization grant JWTs enabled on your OAuth client. After a few business days, a client certificate signed by Tink will be sent back to you. The private key will now be ready to be used for authentication towards the Tink API.

The returned client certificate functions solely as a receipt including the expiration date by which you need to perform a renewal unless you later want to enable [mutual TLS authentication](/Tiny-doc/tink_docs_home/resources/getting-started/set-up-mutual-tls-authentication/) on your OAuth client.

### Enforcing the use of authorization grant JWT[](#enforcing-the-use-of-authorization-grant-jwt)

Once authorization grant JWTs are enabled on an OAuth client, and you no longer need to use the client secret for authentication, reach out to your Account Manager or Tink Support again in order to disable it.

### Creating an authorization grant JWT[](#creating-an-authorization-grant-jwt)

JSON Web Tokens are an open, industry-standard [RFC 7519](https://tools.ietf.org/html/rfc7519) method for representing claims securely between two parties.

Visit [jwt.io](https://jwt.io/) to learn more about JWTs and how to use them.

The required claims in the JWT claim set are shown below. They may appear in any order in the claim set.

| Name | Description |
| --- | --- |
| iss | Id of the client requesting the access token in `tink://auth/client/<client_id>` format |
| sub | Id of the subject in the requested access token: `tink://auth/client/<client_id>` for a client access token or `tink://auth/user/<user_id or external_user_id>` for a user access token |
| aud | Identifier of the audience of the token. Must be `https://api.tink.com/api/v1/oauth/token` |
| exp | Epoch timestamp of when the authorization grant JWT expires. Must not be more than 5 minutes in the future |
| jti | A unique identifier of the authorization grant JWT generated by the client in any format preferred. Used to ensure that JWTs are not replayed. |

All additional claims and headers will be ignored.

The token must be signed with one of the private keys that you’ve generated during the previous steps.

#### Example[](#example)

Create an authorization grant JWT

```
#!/usr/bin/env bash
set -euo pipefail

b64url() { base64 -w0 | tr -d '=' | tr '+/' '-_'; }
json() { jq -c . | LC_CTYPE=C tr -d '\n'; }
sign() { openssl dgst -binary -sha"$1" -sign <(printf '%s\n' "$2"); }
sign_jwt_ec() { openssl asn1parse -inform DER -in <(sign "${1#ES}" "$2") -offset 2 | grep -o "[0-9A-F]\+$" | tr -d '\n' | xxd -r -p | b64url; }

sign_jwt() {
  payload="$1"
  private_key="$2"
  alg="ES256"
  header=$(create_header "$alg")
  signing_input="$(json <<< "$header" | b64url).$(json <<< "$payload" | b64url)"
  sig=$(printf %s "$signing_input" | sign_jwt_ec "$alg" "$private_key")
  printf '%s.%s\n' "$signing_input" "$sig"
}

create_header() {
  cat << EOM
{
  "typ": "JWT",
  "alg": "$1"
}
EOM
}

create_payload() {
  iat=$(date +%s)

  cat << EOM
{
  "iss": "tink://auth/client/<client_id>",
  "sub": "tink://auth/client/<client_id>",
  "aud": "https://api.tink.com/api/v1/oauth/token",
  "exp": $((iat + 300)),
  "jti": "$RANDOM"
}
EOM
}

payload=$(create_payload)
private_key="$(< my-oauth-client.key.pem)"
# private_key="$(< jwt-io-es256.key.pem)" # test keys and verification available at https://jwt.io/

sign_jwt "$payload" "$private_key"
```

### Generate the access token request[](#generate-the-access-token-request)

After generating the token, an application can use it to request an access token using an HTTP POST request to:

```
https://api.tink.com/api/v1/oauth/token
```

The following parameters are required in the request:

| Name | Description |
| --- | --- |
| grant\_type | Use the following string: `urn:ietf:params:oauth:grant-type:jwt-bearer` |
| assertion | The authorization grant JWT generated in the previous step |
| scope | Space-separated list of requested scopes |

You can find more detailed documentation about the endpoints in the [API documentation](/Tiny-doc/tink_docs_api/api/#general/oauth/get-access-token)

#### Example[](#example)

Generate the access token request

```
curl --verbose -X POST https://api.tink.com/api/v1/oauth/token \
-d 'grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer' \
-d 'assertion=' \
-d 'scope=requested:scope1 requested:scope2'
```

### Handling the response[](#handling-the-response)

If everything is correct, you’ll get a response as defined in the [API documentation](/Tiny-doc/tink_docs_api/api/#general/oauth/get-access-token):

```
{
  "access_token": "<access_token>",
  "expires_in": 7200,
  "scope": "requested:scope1 requested:scope2",
  "token_type": "bearer"
}
```

Once the access token is acquired, you can use it to make requests to the [Tink API](/Tiny-doc/tink_docs_api/api/).
